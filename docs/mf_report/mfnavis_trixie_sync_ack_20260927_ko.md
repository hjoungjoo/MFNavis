# 2026-09-27 실내 GoTo Sync 거절 및 확인 응답 수정

## 실제 재현

이전 변경 `00283004` 적용 후 사용자가 GoTo를 요청했지만 실제 이동은
시작되지 않았다. 실행기 상태는 `waiting_sync_coordinates`에서 거절 또는
시간 초과였다. 솔빙 실패 자체나 시리얼 연결 실패가 아니라 마운트 정렬
단계에서 멈춘 것이다.

연결된 INDI 서버를 직접 조회한 `Slew elevation Limit` 값은
`minAlt=-10`, `maxAlt=80`이었다. 사용자는 상한 85°로 알고 있었지만
당시 드라이버가 실제로 내보낸 값은 80°였다. 드라이버 소스는 `:Go#` 응답을
`maxAlt`에 게시한다. MFNavis의 연결된 마운트 제한 조회는 해당 값을 사용하고
80°를 고정으로 덮어쓰지 않는다. 이 점검에서 고도 제한을 변경하지 않았다.

이동 없이 IMU 좌표 Sync만 보내 확인한 결과:

- IMU 고도 약 81.4°: `:CM#` 응답 **`E2`**, 드라이버 오류
  `Above Overhead limit`. 컨트롤러 상한 때문에 정렬이 거절됐다.
- 현재 마운트 readback 좌표를 그대로 Sync한 별도 진단: `E1`,
  `Below the horizon limit`. 정렬 전 마운트 프레임 좌표는 IMU와 크게 달랐다.
- 사용자가 장비를 내려 IMU 고도가 약 61.7°가 된 후: `:CM#` 응답
  **`N/A`**, `OnStep: Synchronization successful.`. 실제 Sync 성공을 확인했다.

성공한 Sync에서도 좌표 응답이 `Idle`로 게시되는 경우가 있었다.
또 실패 시 `Alert` 직후 주기적인 `Idle` telemetry가 게시됐다.
기존 실행기는 최신 응답 하나만 저장하고 `Ok`만 기다렸으므로 실패 원인이
시간 초과로 바뀌거나 성공한 Sync를 확인하지 못할 수 있었다.
디버그 Off 상태의 재검증에서는 성공 `Ok` 응답도 확인했다.

## 수정

- 속성별 최근 응답 32개를 보관하고 현재 요청 이후의 확인 응답을 검사한다.
  짧은 `Ok`/`Alert`가 뒤따르는 `Idle`에 덮여 사라지지 않는다.
- OnStep의 `Idle` 좌표는 **현재 Sync 단계에서 성공 메시지를 받았고**,
  새 서버 좌표가 요청한 좌표와 허용 오차 안에서 일치할 때만 확인 응답으로
  인정한다. 메시지만 있거나 오래된/다른 좌표이면 GoTo를 보내지 않는다.
- 드라이버의 실제 `[ERROR]` 메시지를 로그와 Sync 실패 이유에 보관한다.
  이전 요청이나 이전 클라이언트의 오류는 새 요청에 붙이지 않는다.
- IMU Sync 전에 현재 INDI 고도 제한을 확인하고 범위를 벗어나면 정렬·이동
  명령 없이 고도와 제한값을 상태/LCD 오류에 표시한다. 고정 80°가 아니라
  연결된 마운트 값을 사용하며, INDI 값이 85°로 바뀌면 다음 요청부터 반영한다.

## 검증

수정한 정렬 실행기로 실제 INDI Sync 및 모드 확인 응답을 검증했다.
이 독립 검증에서는 실제 GoTo 함수와 Tracking On 전송을 가로채므로
실제 이동 명령은 보내지 않는다. 런타임 서비스 큐와 상태 파일도 사용하지 않는다.
Sync와 제한 조회는 실제 장비에서 수행했고, 정렬 응답 순서·실패 보존·오래된
응답 차단·80/85° 변경 반영은 자동 테스트로 검증했다.

실제 INDI 응답을 사용하는 독립 검증은 `state=goto_sent`, 좌표 확인 오차
`verified_error_arcmin=0.0`까지 진행했다. 여기의 `goto_sent`는 실제 GoTo
함수를 가로챈 검증 결과이며 실물 이동의 성공을 뜻하지 않는다.

관련 테스트 **316 passed**, Ruff 및 포맷 검사 통과(407개 파일).
Idle 성공 응답 사례 2개와 최종 구현을 포함한 전체 회귀 검증은
**3,609 passed / 3 skipped**, 212.51초였다.
웹 Selenium 테스트와 하드웨어 import가 필요한 IMU 런타임 테스트는
이 회귀 실행에서 제외했다. 실제 IMU 및 마운트 동작은 실장비에서 별도 확인했다.

2026-09-27 **01:37:46 KST**에 기존 허용 명령으로 서비스를 재시작했다.
active/running, PID 176170, NRestarts 0, 마운트 연결 정상, 이동 없음,
추적 On 상태를 확인했다. 임시 IMU 기준 옵션과 실제 INDI −10°~80° 제한을
유지했다. 이전에 거절된 GoTo를 재기동 후 자동 실행하지 않는다.

## 사용자 GoTo 실물 재시험

수정본 적용 후 사용자가 웹에서 GoTo를 다시 요청했고, **실제 이동이
시작되었다고 확인했다**. 01:39:25 KST의 요청
`e33eaaeb4d3e4376ac2b9c28c0fe377f`는 임시 IMU 좌표 정렬에 성공했고
`verified_error_arcmin=0.0`, `state=goto_sent`로 진행했다.

이후 마운트 readback은 목표 RA 1.4671°, Dec 3.3809° 부근인
RA 1.4708°, Dec 3.3806°였고, 이동 완료 상태와 `tracking_enabled=true`를
확인했다. 서비스는 `phase=native_tracking`,
`last_action=native mount tracking; waiting for plate solve`로 전환됐다.
실내 솔빙 실패 중에도 실제 GoTo와 마운트 추적으로 이어진 결과다.
실외 솔빙 복구 후의 실제 미세보정은 이 실내 재시험으로 검증하지 않았다.
