# MFNavis 마운트 제어와 GoTo·보정

기준: 2026-10-10 작업 트리. GoTo 시작, 도착 확인, 솔빙 소실 대기, 추적 보정,
사용자 정렬·취소·정지, 이동 한계 정지를 한 문서에서 관리한다.

## 소유권과 연결

`main.py`가 생성한 GoTo/Guide 서비스는 사용자 의도와 상태 전환을 관리하고,
`mountcontrol_indi.py`는 INDI 연결·명령 전송·상태 수집·실제 정지를 담당한다.
LCD, 웹, SkySafari는 같은 명령 경로를 사용한다. 큐에 넣은 명령과 드라이버의
수락 응답, 물리 이동 완료, 광학 도착을 서로 구분한다.

| GoTo Type | 동작 |
|---|---|
| `off` | GoTo 거부 |
| `indi_mount` | 네이티브 마운트 GoTo |
| `mfnavis` | 광학 앵커·검증된 Sync+GoTo·도착 확인·보정 상태기계 |

INDI Web Manager는 `8624`, INDI 서버 기본 포트는 `7624`다.
설치 후 웹 INDI 화면에서 서버·장치·Serial/Ethernet 전송을 설정하고,
실제 연결 상태와 위치·시각을 확인한다. Serial Auto와 재연결은
[연결 문서](connectivity_ko.md), 다중 정렬과 백레시는 [정렬 문서](alignment_ko.md),
선택형 smooth/영상 추적은 [추적 문서](tracking_ko.md)를 따른다.

## 2026-10-10 GoTo 시작부터 추적 보정까지 검증한 설계

이 절은 현재 작업 트리의 `indi_goto_guide_service.py`, `mountcontrol_indi.py`,
`guide_holdover.py`, `mount_motion_limits.py`와 자동 테스트를 대조한 기준이다.
이 문서를 현재 동작의 기준으로 사용한다. 과거 설계는 별도의 주제별 이력에 보관한다.
검증 범위는 **MFNavis 기본 GoTo/Tracking Guide**다. `indi_mount`는 네이티브
GoTo만 수행하며 `off`는 GoTo를 거부한다. 선택 기능인 smooth tracking은 별도
제어권·광학 품질 정책을 사용한다. 이동 한계 인터록은 smooth timed pulse에도 적용한다.

### 처리 계층과 판정 기준

| 계층 | 역할 | 다음 단계로 넘어가는 증거 |
|---|---|---|
| LCD·웹·SkySafari | 타겟, GoTo, 정렬, 수동 이동, 취소·정지 요청 | 큐에 사용자 의도를 전달 |
| GoTo/Guide 서비스 | 초기 이동·도착·추적·복구 상태 전환 | 최근 마운트 상태와 해당 이동 이후 촬영된 유효 solve |
| 마운트 실행기 | SYNC/GoTo, 가이드 펄스, 실제 한계 검사와 정지 | 현재 연결의 새로운 INDI 응답, 이동 상태, 펄스 종료 시각 |
| `GuideHoldover` | 마지막 측정 오차·실행한 보정량·확인된 표류 속도 기록 | 관측과 추정을 구분하고 같은 오차를 중복 누적하지 않음 |

마운트가 멈췄다는 것과 광학적으로 타겟에 도착했다는 것은 별개다.
`goto_completed_wall`은 마운트 정지 확인 시각이며, 도착 판정에는 그 이후의
solve가 필요하다. 광학 기준은 `pointing.aligned.solve`이고,
IMU로 진행한 `pointing.aligned.estimate`나 마운트 좌표를 새 solve로 취급하지 않는다.
정밀 보정 단계는 유효한 최근 성공 프레임을 계속 사용할 수 있지만, 이미 소비한
프레임으로 PID를 다시 실행하거나 펄스 종료 전 프레임으로 최종 도착을 확정하지 않는다.

### GoTo 시작과 도착 판정

```mermaid
flowchart TD
    A[사용자 GoTo 요청] --> B{모드·타겟·마운트 상태 확인}
    B -->|거부 또는 한계 정지 유지| R[원인 표시 / 이동하지 않음]
    B -->|MFNavis| C{초기 앵커 확보?}
    C -->|유효 solve 또는 허용된 IMU 앵커| D[MFNavis 좌표로 SYNC / 새 좌표 응답 확인]
    C -->|없음| I[초기 수락 대기 최대 12초]
    I -->|앵커 확보| C
    I -->|기한 초과| R
    D --> L{동기화된 현재 좌표와 목표의 한계 검사}
    L -->|초과| R
    L -->|정상| N[Tracking ON / SLEW 응답 확인 / GoTo]
    N --> E[마운트 이동 및 실제 정지 확인]
    E --> F{정지 이후 유효 solve?}
    F -->|없음| W[마운트 추적 유지 / 솔빙 대기]
    W -->|복구| F
    F -->|있음| G{타겟 오차}
    G -->|목표 정확도 이내| H[최종 Sync 요청 / 광학 도착 complete]
    G -->|펄스 진입 조건 충족| P[INDI timed pulse 미세 보정]
    G -->|재GoTo 필요| D
    P --> Q{펄스 종료 이후 유효 solve?}
    Q -->|없음| W
    Q -->|있음| G
    H --> T[Tracking Guide가 켜져 있으면 추적 보정]
```

1. 새 GoTo는 이전 도착·복구·보정 횟수를 초기화한다. 초기 IMU 앵커는 기존
   설정과 유효성 조건을 만족할 때만 허용한다. **초기 수락 대기 12초**와
   **이미 수락한 GoTo 중 솔빙 대기**는 다르다. 후자에는 만료 시간이 없다.
2. `sync_and_goto`는 현재 연결에서 새 `ON_COORD_SET=SYNC` 응답 → 요청과
   일치하는 좌표 응답 → 동기화 좌표와 목표의 한계 검사 → Tracking ON →
   `ON_COORD_SET=SLEW` 응답을 확인한 뒤 GoTo를 보낸다.
   이전 캐시나 단순 송신 성공만으로 다음 단계를 진행하지 않는다.
   MFNavis GoTo·IMU 폴백·추적 복구는 동기화 전의 마운트 좌표로 한계를
   판정하지 않는다. 컨트롤러가 보고한 한계 오류와 이미 잠긴 정지는 계속 적용한다.
3. 실행기는 INDI Busy·OnStep 완료·좌표 안정화를 확인한다. 검증된 빠른 정지는
   1초, 일반 경로는 2.5초 안정화를 사용한다. 같은 이동의 정지 시각이 있으면
   서비스가 별도 정착 시간을 중복 추가하지 않는다. 타임아웃으로 가정한 완료는
   검증된 정지 시각을 제공하지 않는다.
4. 목표 정확도 `A`는 `indi_goto_refine_accuracy_arcmin`이며 서비스 폴백은 1′,
   최소는 0.1′다. 실제 저장 설정을 우선한다. 근거리 범위 `N`은
   `min(max(A, 설정 근거리 도수 × 60), 15′)`다. `오차 ≤ A`는 도착,
   정상 펄스 진입 범위는 `P = min(N, 3 × A)`로 좁힌다.
   `A < 오차 ≤ P`는 펄스 보정, 그 밖은 새 solve를 이용한 SYNC+GoTo다.
   작은 재GoTo 이후 오차 개선이 1′ 미만이거나 해당 GoTo 묶음의 횟수를
   소진한 경우, 펄스가 정상인 대상은 `N` 이내에서 펄스로 마무리한다.
   광학 도착 전에는 펄스 비수렴·지원 불가가 확인되면 오차가 작아도 새 solve 기반
   SYNC+GoTo를 이어간다. 진행 중 정상 펄스의 허용 범위는 `N`을 유지한다.
5. 근거리 접근은 자동 수동 이동이 아니라 **INDI timed guide pulse**다.
   정상 광학 보정은 축별 PID와 확인된 가이드 속도를 사용하고, OnStep은 같은
   축의 타이머를 새 명령으로 교체한다. 기본 최대 펄스는 2.5초다.
6. GoTo 10회/복구 5회는 한 묶음의 한도다. 소진하면 타겟을 유지하고 10초 뒤
   새로운 solve로 다시 시도한다. 90초 미세 보정 정체도 새 관측을 기다리는
   재시도 경로이며, 솔빙 실패 시간만으로 타겟을 취소하는 타이머가 아니다.
7. `complete`는 **광학 오차가 목표 정확도 이내라는 서비스 판정**이다.
   `final_sync_sent`는 최종 Sync 요청을 큐에 넣었다는 뜻이며, 초기
   `sync_and_goto`의 검증된 응답과 같은 의미가 아니다. 최종 Sync 실패는
   실행기의 `sync_failed` 상태로 별도 보고된다.

광학 도착은 추적 보정의 새 기준을 설정한다. 초기 접근에서 실패한 펄스는
검증된 재GoTo와 새 광학 도착 전까지 재활성화하지 않는다. 도착 뒤에는
`reset_convergence`로 추적 펄스 기준을 한 번 초기화한다. 광학 도착 후에는
펄스 실패만으로 작은 오차를 재GoTo하지 않는다. 설정된 추적 GoTo 임계값을
넘는 새 solve가 있어야 재GoTo하며, 복구 직전에도 오차를 다시 확인한다.
추적 펄스가 실패해 재GoTo한 경우에도 정지 후 새 solve로 정상 펄스 진입 범위에 돌아온 것을
확인하면 펄스로 복귀한다. 구름 통과만으로 실패 판정을 지우지 않으며,
이미 소비한 solve와 펄스 이후 관측 경계는 보존한다.

LCD Push의 `native_tracking`은 솔빙 대기(`WAIT`)로 표시한다. 도착 테두리는
`complete`/`tracking`이면서 `optical_arrival_confirmed=true`일 때만 그린다.
사용자가 정렬로 도착을 확인한 `arrived_waiting_solve`는 별도 도착·솔빙 대기
문구로 표시한다.
광학 도착 후 마지막 성공 solve가 12초를 넘기면 완료 테두리를 0.5초 간격으로
점멸한다. IMU 좌표 갱신이나 실패한 solve 시도는 이 유효시간을 연장하지 않는다.
새 solve에 성공하면 고정 표시로 복귀한다. 정지·취소로 GoTo가 해제되거나 추적이
꺼지면 고정·점멸 여부와 관계없이 테두리를 숨긴다. 이는 표시 변경이며 솔빙 소실
중 마운트 추적과 잔여·표류 보정 정책은 그대로 유지한다.

### 도착 전 솔빙 실패와 사용자 정렬

아래는 현재 구현이다. 사용자 정렬 후 현재 영상 위치로 보정을 시작하고 첫 유효
solve의 좌표로 이어가는 변경은 [무솔빙 정렬 후 영상 추적 설계](solver_ko.md#무솔빙-goto-대기-중-정렬-처리)에
정의했으며 아직 운영 경로에 구현되지 않았다.

```mermaid
flowchart TD
    A[도착 전 솔빙 사용 불가] --> B[기존 이동·유한 펄스 종료 후 네이티브 추적으로 대기]
    B -->|실패 지속| B
    B -->|사용자 수동 이동| C[보정 중지 / 이동 종료 위치에서 네이티브 추적]
    C --> B
    B -->|LCD 정렬 또는 SkySafari Align| D[arrived_waiting_solve / 사용자 도착 확인]
    D -->|실패 지속| D
    D -->|확인 이후 새 유효 solve| E[실제 solved 좌표를 추적 타겟으로 한 번 고정]
    E --> F[complete / 정상 추적 보정]
    B -->|사용자 확인 없이 solve 복구| G[원래 GoTo 도착 오차 평가]
    C -->|정렬 없이 정착 후 solve 복구| M[기존 수동 재타겟 정책 적용]
    D -->|취소·정지·모드 변경| X[대기 해제 / 자동 복구하지 않음]
```

- 솔빙이 끊겼다는 이유만으로 추가 IMU/마운트 좌표 GoTo를 보내지 않는다.
  이미 승인되어 실행 중인 네이티브 슬루·유한 펄스는 종료를 기다린다.
- 수동 방향키 해제는 축 이동을 정지하고 네이티브 추적을 유지한다.
  전체 Stop과 다르다. 새 타겟은 이동 종료 및 정착 이후의 solve로 결정한다.
- 사용자 정렬은 솔빙이 없는 상태에서도 도착 의도를 확정한다. 이때 좌표를
  solve로 위조하거나 카탈로그 좌표로 복귀하는 GoTo를 만들지 않는다.
- 복구된 첫 유효 solve가 실제 추적 타겟을 정한다. 이후 프레임마다 타겟을
  다시 바꾸지 않는다. 사용자 확인 이전·이동 중·펄스 종료 이전 프레임은 제외한다.
- 취소/정지/새 GoTo는 이 대기를 무효화한다. 이번 점검에서 취소 후
  `arrived_waiting_solve` 표시가 남는 문제를 재현하여, 대기 상태와 이유도
  함께 초기화하도록 수정했다. `clear_tracking_target`, 보정 중단, 모드 변경
  세 가지 취소 경로에 회귀 테스트를 추가했다.

### 도착 후 추적과 보정

```mermaid
flowchart TD
    A[광학 도착 확인 / 고정된 추적 타겟] --> B{Tracking Guide 허용?}
    B -->|꺼짐·사용자 중단| O[자동 보정 없음]
    B -->|켜짐| C{유효 solve 확보?}
    C -->|있음| D[오차 측정 / 정상 PID 펄스 또는 큰 오차 복구 GoTo]
    C -->|없음| H[solve_holdover / 네이티브 추적 유지]
    H --> R[마지막 잔여 오차 + 확인된 표류 누적 - 실행한 보정량]
    R --> P[유한 펄스로 남은 보정량 수행]
    P -->|실패 지속| H
    H -->|새 solve 복구| D
    D --> C
    H -->|사용자 취소·정지| S[보정 기록 초기화 / 자동 복구 해제]
    L[어느 단계든 실제 이동 한계 초과] --> E[한계 초과 표시 / 축 Abort와 Tracking OFF]
    E --> K[명령 무효화·정지 유지 / 솔빙 복구로 재시작하지 않음]
```

축별 보정 잔량은 `r(t) = e₀ + v × (t − t₀) − (p(t) − p(t₀))`다.
`e₀`는 마지막 solve의 오차, `v`는 광학 관측으로 확인한 오차 증가 속도,
`p`는 송신이 수락된 펄스의 속도와 경과 시간으로 추정한 누적 이동량이다.
이는 명령 기반 계산이며 실제 축 이동을 별도 센서로 실측한 값은 아니다.

- 같은 오차를 매 tick 다시 더하지 않는다. 축 타이머 교체 시 이전 펄스는
  실제로 경과한 명령 시간까지만 계산한다. 장시간 기록은 누적값으로 축약한다.
- 표류 속도는 펄스 이동을 보상한 독립 관측에서 학습한다. 0.5~12초 관측 간격,
  같은 부호의 연속 두 속도 추정, 0.2~5″/s 범위와 일관성 검사를 사용한다.
  빠른 연속 프레임도 최소 0.5초 구간으로 묶어 학습한다. 확인된 속도가 없으면
  0으로 두고 마지막 잔량만 처리한다. 솔빙 실패 시간만으로 속도를 만료하지 않는다.
- 잔량이 1″ 이상 쌓이면 확인된 가이드 속도로 최대 2.5초의 펄스를 보낸다.

  다시 넣지 않으며, 솔빙 실패만으로 수렴 실패 횟수를 증가시키지 않는다.

  추적 단계의 초기 잔량으로 이어받는다. 이전 PID 명령을 재실행하지는 않는다.
- 새 solve는 추정 잔량을 실제 관측 오차로 교체한다. 작은 오차는 정상 펄스 보정,

- 연결 상실, 주차, 드라이버 거부·지원 불가, 사용자 보정 Off는 솔빙 실패와

### 모든 단계의 이동 한계와 정지 우선순위

실행기의 한계 검사가 서비스의 도착·솔빙 복구 판단보다 우선한다. 실제 INDI
고도 한계(`minAlt`, `maxAlt`), GEM 현재 피어 측의 자오선 한계, OnStep의
고도·축·리미트 스위치 오류를 검사한다. GPS 잠금이 없어도 마운트의
`GEOGRAPHIC_COORD`가 있으면 해당 위치를 사용한다. 정렬 별 선택의 기본
20~78도나 과거의 고정 10도 값을 물리 한계로 대신 사용하지 않는다.

연결 준비에서는 현재 연결 세대의 실제 INDI 좌표 업데이트를 기다린다. OnStep은
고도 한계의 실제 업데이트도 확인한다. 추적 중 좌표가 일정하면 OnStep 드라이버가
좌표 업데이트를 생략하므로, 현재 연결의 5초 이내 **Ok 상태 좌표 정의**도 연결
준비에 한해 허용한다. 이 정의는 Sync ACK나 복구용 새 좌표 업데이트로 인정하지 않는다.
Idle/Busy/Alert 상태의 초기 정의 또는 기본 고도 한계만으로는 준비되지 않는다. 확인 전에는
이동 준비를 완료하지 않으며, 제한시간 내 수신하지 못하면 연결 실패로 보고한다.
실제로 측정된 RA/Dec=0은 유효한 좌표이므로 값 자체를 금지하지 않는다.

실내에서 GPS 잠금이 없으면 사용자가 저장한 기본 관측지를 위치·시간 초기화에도
사용한다. 좌표 표시에만 기본 관측지를 쓰고 마운트는 GPS를 무기한 기다리던 경로를
수정했다. 초기화 명령에 위도·경도·고도를 함께 전달하므로 잠금이 없는 shared state를
다시 읽어 위치를 잃지 않는다. 저장 관측지가 없으면 임의 위치를 보내지 않으며,
이후 GPS 잠금과 유의미한 위치 변화가 확인되면 실제 위치가 우선한다.
OnStep의 `Outside limits` Sync 거부는 물리 한계 외에 날짜·시간 미준비에서도
발생할 수 있다(`Limits::isGotoError`). 오류 문구만으로 피어 방향 문제로 단정하지 않는다.

### 카메라 Push 이동량 한 줄 표시 (2026-10-11)

상단 제목 아래 정보 배경을 실제 글자 경계 높이와 여백에 맞추고, 하단 이동량은

좁은 화면에서는 작은 글꼴을 먼저 사용하고, 그래도 부족할 때 선택적인 좌표
출처 표기를 생략한다. 두 축의 방향·부호·작은 이동량 정밀도는 유지한다.

이동량은 솔빙 유무에 앞서 유효한 표시 좌표를 선택한다. MFNavis 모드에서는
현재 광학 좌표 또는 IMU 추정/대체 좌표를 사용하고, INDI mount 모드에서는
마운트 좌표를 사용한다. 좌표 서비스가 발행한 `display`, `solved`, `imu`,
`mount` 표본을 사용하며, 출처는 `S`(솔빙), `I`(IMU), `M`(마운트),
시각 추정 표본이 있으면 `V`로 표시한다. 위치·시각이 필요한 Alt/Az 계산은
기존 공통 좌표 변환을 사용하고, EQ 이동량은 GPS 없이도 계산할 수 있다.

오래되거나 유효하지 않은 좌표, 이전 정렬 중심의 좌표는 제외한다. 사용할
좌표가 없으면 한 줄 `--  --`를 표시한다. 정렬·추적·보정에 쓰이는 공유 상태는
변경하지 않으며, 연결 상실을 이유로 중지 명령을 보내는 동작도 추가하지 않는다.
128·176·320 화면의 실제 글꼴 렌더링과 S/I/M 표시 예시는
`telemetry/20261011_push_ui/push_*.png`에 저장했다. 실내에서는 서비스 재시작
없이 소스에 반영했으므로 다음 정상 시작부터 적용된다.

### SkySafari GoTo 복구·근거리 보정·Push 표시 검증 (2026-10-13)

기준은 `63cb75d0` 이후 이번 수정이다. SkySafari에서 GoTo를 실행해도 움직이지
않던 현상, 도착 뒤 큰 재보정과 솔빙 점멸, Push 확대·마크 표시를 함께 점검했다.
사용자는 모터 전원이 켜져 있고 USB 연결 중 모터 전원을 따로 껐다 켜지 않았다고
확인했다. OnStep의 좌표 신뢰가 해제된 상태에서 Sync가 거절되는 복구 경로를 보완했다.

#### 적용 내용

- 정상 초기화 후 OnStep Sync의 `Unspecified Error`에도 자동 초기화 복구를
  예약한다. 새롭고 정상인 정지 상태, 비주차·비추적·무결함·무한계 상태를 확인하고
  같은 세션의 자동 리셋 예산은 한 번으로 제한한다. 사용자 Stop·새 제어 요청은
  취소하며, 오류 정리용 Stop은 복구를 취소하지 않는다. 실패한 GoTo를 자동 재전송하지 않는다.
- 재부팅 후 기존 마운트 상태 보존을 해제하고 위치·시간·추적 초기화를 다시 수행한다.
- 가까운 축 오차에서는 요청 이동량을 25%로 줄이고 먼 오차로 갈수록 부드럽게
  전체 이동량까지 늘린다. 적분·미분 항도 근거리 상한을 넘지 못한다. 최대 펄스는
  기존 2.5초를 유지하며, 먼 위치 접근 속도의 보편적 향상을 실측으로 확정한 것은 아니다.
- 도착 후 설정 정확도 이내의 잔여 오차에는 재보정을 시작하지 않는다. 진행 중인
  보정은 정확도 절반까지 접근한다. 1~2배 정확도 이탈은 서로 다른 관측 두 개와
  최소 1초의 방향 지속을 확인하고, 2배를 넘는 이탈은 즉시 처리한다.
- 새 영상이 없는 잔여 보정에도 같은 감속·deadband를 적용한다. 마지막 실측이
  허용 범위 안이면 예측 표류만으로 보정을 다시 시작하지 않는다.
- 도착 후 작은 펄스 보정 실패는 즉시 SYNC+GoTo로 승격하지 않는다. 설정된 추적
  GoTo 임계값을 넘는 최신 광학 오차에서만 복구 슬루를 실행한다. 비수렴 판정 간격은
  최대 펄스가 작용할 수 있도록 최소 2.5초로 두었다.
- Push 카메라 배율은 공유 UI RAM 상태로 옮겨 대상·화면 전환에도 사용자 선택을
  유지한다. SD 설정에는 저장하지 않으며 앱을 다시 시작하면 1배부터 시작한다.
- 최대 4배 확대에서는 4도 외곽 원을 숨긴다. 원의 경계 좌표를 대칭 반올림하여
  PIL의 개별 절삭으로 생기던 위·왼쪽 반 픽셀 중심 편향을 제거했다.
  아이피스 정렬 좌표나 솔빙 좌표에 임의의 화면 오프셋을 추가하지 않았다.

사용자가 최종 확인한 표시 편차는 영상상 1~2픽셀이고 아이피스 정렬은 정상적인
기구 오차 범위였다. 유지보수 재시작에서는 기존 handoff로 RAM 정렬을 보존했다.

가이드 축을 물리적인 Alt/Az 축으로 가정했던 중간 시험은 채택하지 않았다.
현재 OnStepX `Mount::poll()`은 timed pulse를 적경·적위에 적용한 뒤 기계 축으로
변환하므로 최종본은 적경·적위 기반 펄스 오차를 유지한다. 해당 판단은 로컬
`OpenX_pio_E4/src/telescope/mount/Mount.cpp`와 OnStepX 소스를 대조했다.

#### 최종 설정과 실측

초기 복구 후 베가 GoTo의 광학 도착 오차 약 0.75′를 확인했다.
후속 보정 튜닝은 데네브·사드르 왕복으로 진행했다.

이번 장비의 저장 설정은 목표 정확도 **1′**, 가이드 속도 **1.0×**,
추적 재GoTo 임계값 **0.1도(6′)**다. 이 값은 현장 설정이며 저장소의 전체 장비
기본값을 변경한 것은 아니다. 0.5× 속도와 물리 축 변환을 사용한 중간 기록을
최종본의 성능으로 합산하지 않는다.

SkySafari와 같은 TCP 4030의 정상 명령 경로로 **데네브 → 사드르 → 데네브**를
실행하고, 각 광학 도착 후 60초를 관찰했다. 카탈로그 좌표는 해당 시각 좌표로
변환해 전송했으며 서비스의 정상 좌표 변환·Sync·한계·도착 판정을 사용했다.

|---|---:|---:|---:|---:|---:|

각 관찰 구간의 120개 상태 샘플 모두 광학 좌표의 freshness가 유지됐다.
독립 solve 시각은 각각 28개·29개였으며, 이는 모든 카메라 노출이 성공했다거나
전체 시험 중 솔빙 소실이 전혀 없었다는 뜻은 아니다. 종료 직후 연결 healthy,
Tracking ON, 광학 도착 complete, 데네브 오차 약 0.80′를 확인했다.

**관측 조건에 대한 사용자 판단:** 중간의 갑작스러운 튐은 바람·구름 등의 영향으로
보인다고 했다. 원시 실측 수치는 그대로 보존하고, 사드르의 오차 증가를 제어기
